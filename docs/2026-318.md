# Update for November 14, 2026

## 09:40 MST

### Starting _Vantage_

Decided to participate in the 2026 NASA Space Apps challenge, the Lunar Landing
Site Navigator seems a interesting one. It seems to be a navigational interface
problem. The data is all out there, but the tools that show it are built for
experts and make comparing sites and dates slow. That gap is exactly the kind of
thing I love working on.

### The name

I went back and forth on the name more than I'd like to admit. I tried a few
short ones like _V1_ and _V01_, but they either carried other meanings or looked
like a beta version. _Vantage_ just felt right. It's a position with a clear
view of what's around it, and it's about choosing the best path before
committing.

### More than light and Earth

The challenge is about sunlight and Earth visibility at the south pole, but I
don't want to build just a lighting calculator. The way I see it, a planner is
picking a place and a time against conditions that keep changing.

Lunar landing conditions are the Sun for power and Earth for a link home.
Tomorrow they could be temperature or slope. So I'm building it as a conditions
navigator, with this challenge as the first case.

The data should come first. The main screen is a simple grid of sites against
dates, with a clear answer in each cell and the reason behind it. I think we can
add visual representation as secondary feedback.

## 16:20 MST

### The data

Out of the challenge resources, JPL Horizons is the one that matters most. It
gives the position of the Sun and Earth from any point on the Moon, which is
exactly the question. Moon Trek can come later for imagery. The site has two
small APIs for now: a list of sites with search and pagination, and Sun and
Earth positions for a site and a date range.

### A small system, no framework

I spent most of the day on the foundation, probably more than I would like to
admit, as a experienced engineer I do think foundations are really important.

I thought about a Go server, but decided to focus on rendering the interface
instead, and run it on Cloudflare as a Worker, built on the same web standards.

I took this as a oportunity to explore some ideas I had about resumability,
react, and serverless runtimes. I built a mini framework oriended in web native
APIs with a router built on URLPattern, Navigation API, and plain links and
forms. One copy of React is shared by the browser and the Worker.

### Data that resumes

The part I like most is how data works. I built `resumable()` to turn any async
function into data a page reads inside a normal `<Suspense>`. The server streams
it and the browser resumes it, so nothing loads twice.

## 17:05 MST

### A new name

I changed the name to _Nanta_, from the Quechua _ñanta_, "the path", the one you
take, from _ñan_, the road, as in Qhapaq Ñan, the Inca road network across the
Andes. I write it without the ñ so it's easier to read in English. _Vantage_ was
too common, and for a navigator I wanted a name about the path itself. It also
feels personal.

## 23:50 MST

### The interface

Took me a while, but I think I have a good idea of the interface now. I wrote
it down as the product design spec so I don't lose it.

I dropped the ranking idea from the last update. A score hides the reason
behind it, and the reason is what a planner actually needs. So Nanta won't
score places. It shows the Sun and the Earth against the horizon for a place
and a date window, and the planner decides.

The flow is three steps, and the URL keeps each one, so back, refresh, and a
shared link all show the same thing:

- Pick a body: the Moon, Mars, or Earth. Each card has the facts that change
  what the horizon means, like whether it has air.
- Pick a place and a window: a short list of sites, and a date window to read.
- Read it: Sun and Earth elevation over the window, with a table of the same
  numbers under it. The table is what a planner can quote, the chart is just a
  picture of it.

For the design I'm following WCAG 2.2, the ARIA Authoring Practices Guide, and
NASA-STD-3001. That means 6:1 contrast for text an operator reads, 3:1 for
everything else, a monospace font with digits that are easy to tell apart, and
light, dark, and auto schemes.
